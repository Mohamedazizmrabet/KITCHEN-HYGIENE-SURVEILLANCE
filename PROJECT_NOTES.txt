KITCHEN HYGIENE SURVEILLANCE — PROJECT SUMMARY

Purpose

This project is a prototype for monitoring personal protective equipment (PPE) in a kitchen. It is intended to detect visible items such as gloves, hairnets and masks, identify possible non-compliance, and present live monitoring and recorded violation information through a web dashboard. The goal is to explore how computer vision and a web application can support hygiene checks; it is a prototype and should not be described as a replacement for human supervision.

How the application is organized

The project is split into three services so each part has a clear responsibility:

- React with Vite provides the browser dashboard, live-monitoring screens, history and model settings. I chose React because its component approach made it practical to build reusable interface elements and update the screen as monitoring data changes. Vite provides the development server and frontend build workflow.
- Laravel provides the application backend for settings, sessions and violation records. It gives the project a structured place to handle web/API requests and persistence.
- Python with FastAPI runs the computer-vision service. Python has the computer-vision and deep-learning ecosystem needed for image/video processing, while FastAPI exposes the inference functions as HTTP endpoints for the other services.
- OpenCV is used for video/image handling; Ultralytics YOLO is used for object detection; Axios connects the React interface to the APIs; Docker Compose describes the local services.

Learning and development

I built the interface by working through the official React documentation and applying those concepts in the dashboard, including components, state and effects. I used the official Vite guide for the frontend development/build setup. For the inference API, I referred to the FastAPI tutorial and used the project code to connect endpoints to the detector and stream logic. Laravel's official documentation was a reference for the backend structure and data handling.

A major part of the learning process was iterative integration: getting the browser UI, Laravel API and Python inference service to communicate, then passing live camera/video frames through the detection and display flow. I also spent time comparing model weights and trying datasets. This exposed how strongly results depend on the labels, class definitions, image quality, camera viewpoint and whether examples resemble the actual kitchen footage.

Why I tried pretrained/downloaded models

I initially trained or fine-tuned models with the datasets available to me. In my tests, performance was not reliable enough, especially when a person or PPE item appeared far from the camera. Distant gloves, masks and hairnets occupy very few pixels, so their visual detail is limited; a model cannot recover detail that is absent from the frame. The results also depend on having enough correctly labelled examples at similar distances, angles, lighting and camera resolutions.

I therefore tried existing model weights available online as a way to compare a stronger starting point and avoid relying only on one training run. A pretrained model is not automatically suitable for this application: its classes, training data, license and performance still need to be checked. An online lookup confirmed that yolov8n.pt is an official Ultralytics YOLOv8 nano detection weight. I could not verify a public source for the exact filenames khawla_v6.pt or khawla_mask_vest.pt, so their publisher, dataset and training history remain unverified. The weight files and code do not keep enough source information to establish those details, so their origin still needs to be confirmed.

Current model configuration found in the code

The default YOLO configuration in inference-service/config.py points to:

- khawla_v6.pt as the primary PPE model.
- khawla_mask_vest.pt as an optional additional mask model.
- yolov8n.pt as an optional person detector, using class 0.

The YOLO detector loads each file if it exists. Therefore, these three files are the active/default model files in this checkout; this does not prove that all three load successfully on every machine. The file named best.pt is not selected by the current configuration. Its name is generic, so it should not be described as the final chosen model without confirming its origin and evaluating it.

YOLO and RT-DETR

I added RT-DETR as a second model option next to YOLO so the two architectures can be compared in the same application. The dashboard lets the user switch between YOLO, RT-DETR or both.

I did not train the RT-DETR model myself. I searched for a pretrained RT-DETR model for kitchen PPE and found none covering gloves, masks and hairnets together. The closest one available is qubvel-hf/rtdetr-r50-cppe5-finetune on Hugging Face: an RT-DETR R50 model fine-tuned on the CPPE-5 medical PPE dataset (Coverall, Face_Shield, Gloves, Goggles, Mask). Its model card reports about 0.58 mAP for gloves and 0.54 mAP for masks on CPPE-5. I integrated it through the Hugging Face Transformers library, since it is not in the Ultralytics format; the detector still accepts an Ultralytics RT-DETR .pt file as well.

Limits of this model for the project: it only detects PPE that is worn (gloves, mask). It has no hairnet class, no person class and no violation classes such as bare hand or no mask. To make it usable for tracking, the RT-DETR mode reuses the same yolov8n person detector as the YOLO mode, and a person is flagged when a glove or mask is not found near them. Hairnet is not checked in RT-DETR mode, so the app does not report false hairnet violations. It was also trained on medical-style images, not kitchen footage. In a quick check on the project's sample images it detected the glove and mask examples and returned nothing for the hairnet images, as expected. On my GPU it ran at about 55–95 ms per frame.

I focused most of my effort on YOLO. It is lighter, runs fast enough for live video on ordinary hardware, and the Ultralytics training workflow made it easier for me to train and iterate on PPE datasets. A fair YOLO vs RT-DETR comparison would need both models trained on the same kitchen PPE dataset, which is a next step.

Challenges and next steps

The most important challenge was inconsistent detection at distance. My local training attempts did not generalize well enough to the camera views I wanted to use. I also had to compare datasets and model files whose classes and label conventions may differ. Combining separate PPE and person models introduces another integration challenge: overlapping boxes, class-name normalization, confidence thresholds and tracking need to work together without duplicate or misleading detections.

Useful next steps are to fine-tune RT-DETR on the same PPE dataset as YOLO, then evaluate both on a held-out set of frames from the intended camera. Report per-class precision/recall and examples at multiple distances, verify class mappings, and collect/label more representative distant examples. Camera placement, resolution, focus, lighting and inference image size should also be checked. Before publishing any weights, check their source licenses and the dataset's redistribution terms.
